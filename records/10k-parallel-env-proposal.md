## 判断

现在值得验证并行收益，但18ms是Lab单线程仿真控制器的自定预算，不是ENV/Protocol固有吞吐上限，不能把它单独作为必须拆所有ECS系统的证据。
当前实测单次观测平均：build6.2446ms、encode0.9375ms、decode0.9461ms。
单帧Agent pump平均14.0969ms，ENV更新+render/present平均14.5847ms，说明两类工作确实串行占用同一个frame。
这些均为当前canonical5000U/1000A/30秒闭环的测量，不能直接外推10K或推导2倍收益。

## 建议的第一条并行边界

保留四层架构。ENV内部划分执行职责，不新增架构层，也不提前接入Protocol/Hub。

| 执行者 | 职责 | 世界写权限 |
| --- | --- | --- |
| ENV owner进程/线程 | 固定1/FPS推进、动作校验和提交、移动/战斗/CD/Fog更新、查询身份校验与快照绑定 | 唯一写入者 |
| 观测worker进程池，先2个 | 在纯数据只读快照上计算阵营视图、逐Unit面板/合法动作和JSON编码 | 无 |
| Lab合成Agent进程 | JSON解码、合成决策、墙钟思考、发送下个请求 | 无，只提交命令 |

第一轮保持现有窗口/渲染在owner侧，避免同时改GUI归属、ECS写入和观测三条边界。后续若render仍挤占世界预算，再单独评估展示进程。

## ECS如何支持并行，以及当前还缺什么

ECS把数据与处理逻辑分开，有利于识别和拆分并行任务，但“通过数据交换”仍然存在数据依赖。多个System从同一个World取组件，相当于读写同一张表，而不是各自收到一份独立消息。模块之间少import不能证明内存读写独立。

当前[World.update](../../star-main/framework/ecs/world.py)按systems顺序同步执行。[CombatSystem.execute_attack](../../star-main/rotk_env/systems/combat_system.py)会读取双方位置、兵力等组件，修改行动点及伤害结果，并触发事件/显示等后续工作；其update本身为空。因此不能只检查System.update，也必须检查命令入口、事件处理和间接写入。

例如，假设B正离开A的攻击范围，同时A攻击B：先移动与先检查攻击可能得到不同结果。将相关代码直接同时运行，会让结果受任务完成顺序影响。需要由博弈规则规定先后关系，不能由CPU调度偶然决定。位置变化还会影响空间占用、Vision/Fog等派生数据；仅复制位置而沿用另一时刻的索引，也不是一致快照。

| 任务之间的数据关系 | 可采用的调度方式 |
| --- | --- |
| 同时读取同一份稳定数据 | 可以并行 |
| 写入不重叠的数据，且没有其他共享依赖 | 可以并行 |
| 一个任务写，另一个需要读取它的结果 | 建立先后依赖，或显式读取固定版本 |
| 多个任务修改同一份数据 | 划分写入所有权，或计算候选结果后统一解决冲突 |

这里的依赖包含组件、索引、事件、缓存、随机数流和实体增删，不能只看组件类型名字。未来可以声明任务的读写集合，再按依赖调度；同一个System内部也可以分批处理Unit，不必固定“一System一核”。例如候选移动可考虑分批计算，但落点争用仍需统一裁决。此类世界写入并行不在首轮实现范围。

成熟的ECS并行实现同样需要调度机制，例如[Unity按组件读写关系追踪Job依赖](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/systems-scheduling-jobs.html)。ECS提供拆分基础，依赖调度负责保证执行正确。

首轮选择本机多进程观测：多个任务只读快照，不需要相互裁决世界写入。跨机器分布式还涉及数据副本、网络传输与故障下的顺序，不作为本轮目标。
当前Python3.13.12实际GIL开启，Py_GIL_DISABLED=0；普通线程不是此类Python CPU任务的默认多核方案。首轮选择多进程，明确计入IPC与序列化成本。
参考：[Python threading](https://docs.python.org/3.13/library/threading.html)、[multiprocessing](https://docs.python.org/3/library/multiprocessing.html)。

## 观测任务的数据划分与复用

目标是把当前观测依赖提取为只读数据接口，让串行与worker尽量共用观测规则，避免复制一套业务逻辑长期维护。以下是设计职责，不代表已有这些接口。

| 数据或结果 | 生成/持有位置 | 复用边界 |
| --- | --- | --- |
| 地图拓扑、未变化的地形规则等静态数据 | worker启动时加载一次 | 地图/规则版本一致；可变地形必须进入动态版本 |
| 位置、兵力、资源、占用、Fog等动态输入 | owner在安全边界导出纯数据 | 同一不可变世界版本；所有相关派生数据必须对应同一时刻 |
| 与请求方无关的Unit事实 | worker按需计算 | 同一版本可供不同阵营投影复用，但不能直接作为跨阵营响应 |
| 阵营可见信息和共享结果 | worker生成阵营投影 | 同版本、同阵营以及其他实际影响结果的上下文一致 |
| Agent认领权限、控制Unit与专属字段 | owner绑定权限，worker装配响应 | 仅该请求的授权上下文；不能只按阵营命中整个响应 |

reachable/attackable是否可共享，要按实际输入决定，包括动态占用、资源预算和规则；本轮不把它们改为仅依赖地图的静态属性，也不删字段或近似视野。

保留“按需生成、同一只读区间复用”的原则：连续接纳的多个查询之间若没有世界写入，可绑定同一个快照。帧号相同不等于数据相同；中间执行过动作或世界更新，就不能仅凭帧号复用。已冻结的旧快照可以在世界推进后继续被worker计算，这与给新查询返回旧缓存是两回事。

第一版允许各worker持有自己的有界缓存，同一版本在不同worker中可能重复计算。这是明确的初始成本，不宣称全进程“只计算一次”。先测任务分配和重复量；确有必要时再评估同版本/同阵营任务亲和分配与负载均衡。跨进程共享可变缓存不作为首版前提。

## 一次观测请求的生命周期

1. Lab客户端提交带request_id和Agent身份的请求；记录原始到期/提交时间。
2. owner在不被其他世界写入打断的安全边界处理身份、参数和权限，分配接纳序号，绑定快照版本。排队等待接纳期间不假称已经拍照。
3. owner导出worker所需的完整纯数据依赖，或复用同一只读区间已导出的版本，然后派发任务。静态数据不随每个请求重复发送。
4. worker只读快照，计算投影和合法动作、编码响应。它不能访问真实World、创建实体、消耗资源、触发战斗事件或推进随机数流；现有查询中的惰性初始化/缓存写入须在接入前审计并隔离。
5. 响应以request_id匹配客户端。内部记录snapshot_id、接纳序号和时序指标，首版不擅自改变公开响应字段。不同Agent可以先后返回；同一Agent首版最多一个在途观测，收到响应后才继续闭环。
6. owner按已定义的命令顺序处理后续动作，并重新检查当前世界合法性。worker响应快慢会影响客户端未来提交时间，但不能绕过动作校验。
7. 完成、取消或失败后释放请求引用；worker确认不再读取时才能释放底层快照。缓存淘汰与取消后的迟到结果处理也必须遵守这个生命周期。

第一版优先使用显式进程启动与可序列化消息，worker仅加载计算所需代码，不初始化窗口、网络客户端或另一个游戏循环。传输方案先选择便于验证的纯数据复制；是否需要共享内存由导出/IPC证据决定，不能只计计算收益而忽略复制成本。

## 关键正确性边界

1. Worker不能读取正在变化的World，也不能复用现有ObservationBatchContext里的活组件引用；现有批次入口明确要求owner线程同步只读，不能直接放进executor。
2. 观测在owner接纳它的确定位置绑定不可变版本，至少包含tick与同帧写入序号。不能仅依赖update边界的World.revision来标识同一帧内多个动作的先后；版本设计必须覆盖所有会影响观测的写入。
3. 动作M → 查询Q → 动作N：Q必须包含M、不能混入N。owner冻结Q所需数据后，N可继续推进，worker完成的是Q当时的世界，不是任意旧缓存。不同Agent响应可以因计算耗时不同而先后返回，每个Agent的请求链和动作提交顺序仍受明确约束。
4. 默认不把请求自动降为“上一帧”观测，不跨若干帧TTL复用。若未来考虑“最新完成帧”语义，必须作为显式Benchmark设置讨论，不能暗中放宽原只读批次规则。
5. 身份/阵营/认领权限在owner侧确定；worker只输出该Agent允许的投影，跨阵营不能泄露私有信息。动作执行时重新对当前World校验所有权、资源、占用和目标合法性，不能把快照的reachable当执行许可证。
6. 已绑定的快照不能被覆盖。按在途请求引用保留版本并设置有界队列；队列满要明确背压/拒绝，不能静默换新快照、丢旧请求或重置原deadline。worker失败不得重复提交动作。
7. ENV模拟秒继续每帧1/FPS推进；外部Agent思考用墙钟。并行化不改变这两个时钟。

## 按阶段验证

### A：澄清客户端与ENV成本

本阶段是观测并行实验的对照准备，不改变“先做观测并行”的优先级。
只把Lab合成Agent解码/动作选择/墙钟调度放入独立进程，仍由owner执行现有业务入口；IPC只替代本地调用，不引入Hub。
对照现有baseline，记录JSON编码/解码、IPC排队和owner服务时间。预期只移除客户端部分，不能宣称移除了6.24ms观测构建。

### B：冻结状态的观测worker原型

从owner导出当前观测所需的纯数据依赖，不复制pygame/锁/整个World。静态地图在worker初始化一次；动态位置、资源、所有权、Fog等按版本提供。
先在完全冻结场景上运行1/2/4 worker，对照生产single路径逐字段/列表顺序/错误响应；包括非空reachable/attackable、敌军过滤与跨owner权限。
必须分别计量导出、复制/IPC、worker构建、JSON编码/解码和版本内存。不能只计worker运行时间，也不能把主进程已经造好完整JSON后的并行编码称为“观测并行”。
先明确导出成本；没有可靠的组件变更账本前，不承诺动态导出O(active)。若全量冻结本身成为新瓶颈，再评估有界的增量镜像，不能依赖不完整World.revision偷偷跨写入复用。

启动前先列出get_faction_state读取的组件、索引、派生状态及隐藏写入，形成快照字段清单。覆盖无Agent/无Unit、单Agent多Unit、同阵营不同权限、不同阵营视野、Unit死亡/认领变化、参数错误等契约。对同一快照重复计算应得到相同业务结果，不改变真实世界或随机数状态。

### C：动态闭环

固定帧内接纳/动作提交顺序，对固定命令回放检查串行与并行的观测版本、World状态和错误结果一致。
再测canonical5000U/1000A/30秒墙钟闭环，24Hz基线、30Hz目标，先2 worker；有效后再扩至4 worker和更大规模。
记录完整世界frameP99/Hz、请求排队+服务P99、snapshot age、快照导出与IPC成本、CPU/RSS、队列增长、实际move/attack/存活/同时移动数及每Agent完成分布。
场景/响应大小改变会影响成本，不能省略布局。随机动态反馈的轨迹随服务速度而变，不声称跨实现随机运行逐帧相同。

动态正确性用例必须覆盖动作M→查询Q→动作N、同帧多次写入、查询连续共享、worker乱序完成、队列满、超时/取消、worker退出和地图重置。检查Q版本明确、无权限混用、无重复动作、无快照提前释放。地图重置必须隔离旧世界的在途结果，不能仅凭重新从零开始的tick匹配。

对照分三组：现有本地串行路径、客户端独立但ENV观测串行、客户端独立且ENV观测并行。后两组尽量保持相同IPC与接纳策略，并加入1 worker对照，以区分进程搬迁、调度变化和真正并行的收益。不得同时调高18ms预算后把全部改善归因于并行。

性能运行保留既有布局、seed、动作概率及闭环：初始错峰0–30秒；观测后提交本轮合成动作，再按墙钟思考，等待为均值30秒、标准差5秒、截断15–45秒的分布。每Unit每轮move/attack/wait概率为50%/25%/25%，无合法目标转wait。思考期间不轮询；每Agent平均控制5个Unit不等于5000Unit同时移动。Chrome保持开启并记录环境干扰。

完整请求延迟从原始到期/提交口径计到客户端解码完成，分开记录接纳等待、快照导出、worker排队、构建/编码、传输/解码；异步阶段可能重叠，不直接相加各段P99。另报响应时快照的墙钟年龄和落后模拟tick数。100ms观测/动作排队阈值沿用为对照诊断项，是否作为最终容量验收硬门槛应单独注明，不能代替世界24/30Hz与队列有界性判断。

先做正确性和短运行排除问题，再用相同预热/测量窗口串行A/B；长期稳定性结论需要相应长窗口证据。冻结场景吞吐和短运行结果不直接登记为新的容量Frontier。

## 成功与停止条件

世界推进和观测尾延迟同时改善，快照一致性/权限/动作顺序通过，版本队列和内存保持有界，才值得集成。
如导出+传输抵消并行收益，保留负结果并重新选择边界；如仅客户端拆分有效，单独报告其收益，避免过度改动生产。
18ms预算不会因为改成进程就自动消失：owner仍需要有界的请求接纳和动作提交策略，只是将大量只读计算移出这段临界路径。
所有性能实验串行；这里的“串行实验”指同机不并跑不同实验，不妨碍单个实验内部的多个worker并行。
原始/compact证据与进度留Lab；生产改动放新codex分支，先tag再squash。P1/P2仍跳过，真实LLM和Protocol/Hub仍不在首轮范围内。
