## 已确认的设计边界

- 本轮唯一优化方向：同一同步只读批次内，按需构建并复用观测中相同的内容。
- 世界30Hz；观测独立从1Hz/Agent起测，再测5/10/30Hz。决策延迟与观测频率独立。
- 用户放弃完全叠格/取消单位阻挡的方案，保留现有落点、路径、Fog和协作规则。
- 用户认同取消兵力损失导致的移动力弱化；该规则修改另行处理，本轮性能A/B使用一致移动规则，不能顺带修改。
- 不引入跨帧TTL缓存、近似情报、丢弃/合并观测请求、压缩观测字段或新的线协议。

## 1. 批次入口与顺序

在ENV的`LLMSystem`新增内部批量观测入口（建议名`process_observation_batch`）。它接收已由本地调度器确认到期的一段有序请求，只允许`get_faction_state`。每项包含可信调用方传入的agent_id/action_id与params；每项仍经`_process_action_request(send_response=False)`进行注册身份、阵营、选定Units和当前match允许动作等原有校验。

批次由ENV所属线程同步完成，没有await、工作线程、调用方回调或世界更新穿插。仅复用可证明不变的游戏观测数据；请求统计/ACK等管理动作不作为共享的游戏事实。单请求接口保留原有独立行为。

Lab只合并当前heap中已经到期、按原顺序连续出现的observe事件。遇到act/注册/认领/释放/任意非观测事件就结束批次，先按原顺序执行事件，再新建下一批。不越过写入，不等待凑满，不提前服务未来deadline。不按阵营重排请求。示例：A读、B读、C移动、D读 => A/B共享一批，C执行，D新批。

入口返回已消费前缀数量、逐请求响应和诊断时间。未处理后缀保持原deadline/serial回到调度队列。参数错误逐请求返回原错误；内部异常结束当前批次并释放上下文，已消费/未消费范围明确，不重放成功请求。

## 2. 快照内容和复用键

一个私有的`ObservationBatchContext`拥有当前批次所有暂存内容（建议置于ENV的utils模块），不是新的架构层或完整World复制。

| 内容 | 复用键/粒度 | 边界 |
| --- | --- | --- |
| 实时Unit census及原始基础事实 | 批次内一次census，Unit ID索引 | 首次合法查询才构建；可一次扫描供各阵营计数，不宣称已经O(active) |
| 已需用地形格子的公开属性 | tile coordinate | 跨阵营复用；可见格子集合仍由阵营Fog决定 |
| 阵营统计、状态、可见敌人/地形列表 | observer faction | 每批每个被查询阵营最多构建一次；先验证查询者身份再取用 |
| 己方Unit详情/合法动作 | faction + Unit ID | 按需构建；敌军基础可见信息不触发详细面板或affordance计算 |
| owner/commandable与最终所选Unit集合 | 逐请求组装 | owner是Unit事实，commandable是Agent与Unit的关系；Agent字段不写入共享对象 |

基础事实可以被多个阵营复用，输出投影必须分开：敌军只允许现有简版字段；不能把己方详细面板直接发给敌人。保留列表顺序、重复ID处理、空选择与错误响应语义。

全局census一旦构建，复用其中已读取的基础字段；详情与affordance仍按实际需求生成，避免为了共享预先为所有居民Unit计算昂贵面板。第一次实现仍允许每批一次O(Nresident) census；收益来自消除每请求重复扫描，细粒度跨批次增量维护不属于本轮。

## 3. 生命周期与结果所有权

批次开始创建上下文；首次访问才填充。同步返回、预算结束、异常退出都在finally中清理，不保留跨批次观测缓存。World.revision只作附加一致性检查；它在World.update开始时增加，不能单独证明一帧内部没有原地写入。

私有上下文只在批量入口内部激活，不能用可跨任意用户代码持有的contextmanager/generator暴露出去。不可在上下文活动期间分派修改游戏状态的动作；意外重入/版本变化结束复用并报告诊断，不能继续输出不一致混合快照。

批量入口逐条构建并按当前stdlib JSON配置编码为独立bytes，在同步批次中完成编码；缓存中的dict/list/组件引用不交给调用方修改。返回值保留每条响应的独立身份和字节内容，不合并成一次逻辑观测。单请求返回dict的原契约不变。

若响应整批返回，则所有响应的真正就绪时间按批次实际返回计量；单条构建/编码结束时间仅作为归因，不能当成已向Agent交付。

## 4. 有界执行

初始默认候选：每批最多32条；每帧沿用12ms Agent处理预算。预算覆盖读取/构建、编码和Lab消费响应，按剩余帧预算传入入口；不因拆成多个批次获得额外帧预算。入口在单条请求之间检查预算，单条不可抢占的超时完整计入整帧。

不为命中率冻结世界或推迟已经排在前面的动作。批次可能只有1条，实际批长与命中率必须测量。资源上限：批次仅持有当前世界的必要暂存数据和最多32条已编码响应；请求队列沿用原有有界表示，逻辑积压用deadline/nominal load展示，不丢负载。

先固定32/12ms完成基线；若后续归因证明需要调整批量/预算，在Lab预注册单变量对照，并保留负结果。不会通过更换JSON编码器或改变GC策略混淆本轮因果。

## 6. 实施顺序和正确性验收

A. 建立受控批量入口，暂不复用内容：保序、预算、异常、编码和独立身份测试先通过。
B. 增加批次上下文和上述按需复用：先公共事实/阵营投影，再同一Unit面板复用。保留单请求参考路径。
C. Lab接入三种对照：原逐请求、相同批次入口关闭复用、相同批次入口开启复用。这样可区分调度变化与缓存收益。

必要契约：
- 同一冻结世界状态下，批量与逐条参考的解析后JSON逐字段相同，包括非空reachable/attackable、Fog开关、空/重复/非法ID、跨阵营拒绝、未注册Agent和禁用动作。
- 同阵营不同owner的两个Agent查询同一Unit，公共事实相同而commandable正确；敌人只收到允许公开的字段，隐身于Fog外的对象不出现。
- 改变位置、AP/MP、兵力/死亡、所属阵营、所有权、Fog或替换/增删组件后，下一批读到新值；包含同帧两批之间的原地修改。
- 读/读/写/读保持顺序；错误和异常不留下有效缓存，不重复已完成请求。
- 修改/消费一个返回响应不能污染另一个响应或下一批数据。
- 构建次数验证：每批一次census，每个查询阵营一次公共构建，每个访问对象/Unit面板按复用键最多一次；无请求不构建。

## 7. 性能验证与发布

先以3000 Units/1000 Agents/独立1Hz观测做上述三路A/B/C。1s决策用于与已归档基线比较；额外以30s决策代表较慢LLM，始终保持1Hz观测，不能互相替代。随后5000/1000，以及10000/1000、5000、10000 Agents的规模诊断；5/10/30Hz观测至少在5000/1000上与原矩阵对照。非空攻击/移动独立场景保留。

每次记录：实际批长分布、公共构建次数/命中率、每Unit/格子的复用次数、首次构建与命中耗时、响应字节/编码时间、完整帧P99、实际世界Hz、逐请求响应/动作排队P99、offered/completed、最老积压和Agent公平性、resident/moving、实际接受/拒绝动作。

只读冻结快照用来证明输出等价；动态反馈运行保留相同配置/种子，但不声称不同服务速度下轨迹逐帧相同。保持Chrome、视口、GC策略、JSON编码、Fog和负载规则一致，不删除慢帧。

正式容量点仍要求一条>=300s和三条独立进程>=60s全部过线：整帧P99<=33.333ms、世界>=29.7Hz、观测排队+服务P99<=100ms、动作队列P99<=100ms、期末最老积压<=100ms、完成>=95%预定观测量，以及原有存活、Fog、世界进度、数据完整性等门槛。短测只用于诊断。

达不到千Agent目标时，报告本项收益及剩余瓶颈，不能把缓存命中当成容量达标。每阶段更新Lab恢复入口；原始和compact包按PROTOCOL.md归档并核验。集成前annotated tag固定开发tip，再且仅以git merge --squash合入main，记录合并前/开发/tag/合并后SHA。
